## 二、上午部分：平台与环境基础

### 2.1 Skill 补充知识（视频01）——面试必问

**什么是 Skill**
- 本质：**一个文件夹**，里面装着"方法 + 资料"
- 必须包含 `SKILL.md`，其中必须写两项内容：
  1. `name`（名称）：这个 Skill 叫什么
  2. `description`（描述）：这个 Skill 干什么、什么时候调用
  
  - 描述写得越详细，Agent 选 Skill 越准（靠描述匹配）
- Skill 本质 = **用提示词写的工作流**（固定的、可复用的规则）
  - 可附带工具调用、规则文档等资源
  - 规则不变就反复复用，改规则只需改对应内容，不用全部重写
- 写作格式：优先 **Markdown**（大模型最易识别），不要写纯 TXT

**从退款场景理解 Skill（799 元退款审批示例）**
- 工作流 = 三步大模型模块：①核对订单事实 → ②读取当前政策（如 V1：超500元转人工）→ ③给出最终建议
- 规则要点：
  - 已退款订单 → 停止重复处理（不能退两次）
  - 带风险标记 → 转人工审核
  - 金额超阈值（如500）→ 人工审批；低于阈值 → 普通审核
  - 政策可版本化：PolicyV1/V2/V3，改政策只需换文档，流程不变

**人在环中（Human-in-the-Loop）——重大事项必须人工确认**
- 退款、医疗报告、金融等高风险场景：智能体只能给**建议**，最终**人工确认**
- 智能体自主决断出错（面对百万次交易），责任由编写者承担

**Skill 三步写法**
1. 写名称 + 描述（适用场景、调用时机）
2. 写具体工作流（做什么）
3. 整理配套资料（规则文档、参考知识库）

**面试真题：为什么用 LangGraph 不用 Skill？**
- Skill 特点：固定、写死在文档里、适合**重复/固定规则**任务
- LangGraph 特点：**自我决策、多条链路、可暂停可恢复、人在环中（HITL）**
- 答题方法论（通用套路，可封装成"面试技巧 Skill"）：
  1. 拆解技术一的原理
  2. 拆解技术二的原理
  3. 分析项目业务需求
  4. 归因：我们的任务需要 X（自我决策/暂停恢复），所以选 A 不选 B
- ⚠️ 面试官问"为什么用A不用B"，80% 不是质疑你，是考你懂不懂底层原理

### 2.2 昨日回顾（视频02）

- **云服务三概念**（面试常考）：
  - SaaS = 软件即服务（到店直接用餐，如在线文档）
  - PaaS = 平台即服务（提供厨房自己备料做菜）
  - BaaS = 后端即服务（后厨全托管，只管前台）

- **Dify vs 扣子**：扣子线上直接可用；Dify 需本地部署，流程繁琐
- **WSL**：Windows 下的 Linux 子系统（支持 Ubuntu/CentOS），16G 内存可能崩溃；Docker 不适配 Windows，需先装 WSL
- **Docker 两大核心**：镜像（打包好的完整环境包）+ 容器（镜像运行出的实例）；解决不同环境部署适配难题

### 2.3 Docker 和虚拟机基本介绍（视频03）

**为什么学 Docker**（7.5 版本新增考点，面试部署类问题 5%-10%）
- 痛点：不同用户/客户机器环境差异大，逐台配置效率极低
- Windows 解决路径：配置好 → WSL 构建 Docker 镜像；配置一般 → 虚拟机

**虚拟机**
- 传统虚拟化：一套操作系统内运行多套独立子系统，主流软件 VMware
- 缺点：资源占用多（独占内存/磁盘）、步骤冗余、启动慢、并发上限低
- 类比：物理机=独栋别墅；虚拟机=同楼层独立房间

**Linux 容器（LXC）/ Docker**
- 进程级隔离（非操作系统级隔离），共享宿主机内核
- 优势：启动快、资源占用少、体积小、单机可跑成百上千容器
- 类比：货轮上的集装箱 / 胶囊公寓
- Docker = Linux 容器的封装（占市场 90%+，图标大鲸鱼）

**Docker 核心概念**
- 镜像（Image）：只读模板，打包应用+全部依赖；容器（Container）：镜像的运行实例
- 镜像仓库（Registry）：公共仓库 Docker Hub（需科学上网，国内需换源）；私有仓库（企业内部流转，防泄密）
- C/S 架构：`docker build`（构建）/ `docker pull`（拉取）/ `docker run`（运行）
- 常用镜像：Ubuntu、CentOS、Nginx、CUDA、PyTorch 等

**基础命令与实用技巧**
- `docker images` 查看镜像；`docker ps -a` 查看全部容器；`docker exec` 进入容器；`docker logs` 看日志
- `docker run -d` 后台运行；设置 restart 参数实现**容器自动重启**（服务不中断）
- 生产环境：systemd 高级进程托管（替代 nohup）

### 2.4 工作中使用 Docker 和构建（视频04）——实操

**容器 → 镜像 → 私有仓库（企业流程）**
- `docker commit <容器ID> <新镜像名>:<版本>`：把改好的容器打包成镜像
- `docker push` 推到**私有仓库**；同事用 `docker pull` 拉取
- 企业里不会推到公共 Docker Hub

**面试考点：Flask vs FastAPI（为什么用 FastAPI）**
- Flask：同步，每个请求占一个线程，阻塞
- FastAPI：**异步**（async/await 挂起处理），用 Rust 写，更快，天然支持并发
- 业务场景（舆情监控）：每天处理几千万条数据（微博/抖音/小红书/快手/懂车帝/YouTube/X/Facebook…），必须异步
- 答题套路：对比两者底层 → 结合业务并发量 → 所以选 FastAPI

**在线接口限流：RPM / TPM**
- RPM = Request Per Minute（每分钟请求数）；TPM = Token Per Minute（每分钟最大 Token 数）
- 上线前必须确认配额，不够向对接方申请加量，否则超限报错

**Dockerfile 构建镜像**
- 核心内容：`FROM python:3.12-slim`（基础镜像）、`WORKDIR`（工作目录）、`COPY requirements`（依赖）、`COPY`（复制代码）、`EXPOSE`（暴露端口）等
- `docker build -t <镜像名>:<版本> .` —— 末尾**点**代表当前目录，必须与 Dockerfile 同目录
- `.dockerignore` 忽略文件：**`.env` 必须忽略**（含 API Key/密码等敏感资源），日志文件也不用上传
- 现在可用 AI 代写 Dockerfile，但要理解内部含义

## 三、下午部分：RAG 完整链路（核心重点）

### 3.1 RAG 基础概念（视频08）

**什么是 RAG**
- 中文名：**检索增强生成**（Retrieval-Augmented Generation）
- 结合"信息检索 + 生成式 AI"：从知识库检索相关内容 → 交给大模型生成
- 核心作用：动态调用外部知识库，提升 LLM 回答的**准确性、相关性、时效性**

**RAG 两大阶段**
1. **离线建库**：文本 → 切块 → 向量化 → 存入向量数据库
2. **在线检索**：用户 query → 向量化 → 检索 → 融合/精排 → 上下文 + 问题 → LLM 生成

**核心环节是"检索"**：检索的全面性、准确性决定最终效果；生成环节相对简单

**为什么需要向量（语义）**
- 传统关键词匹配痛点：语义相近但表述不同（如"差旅费" vs "出差开销"）匹配不上
- 语义向量：用 Embedding 把文字转为代表语义的向量

**相似度计算**
- 欧氏距离缺陷：受语句长短影响，易误判
- 主流用**余弦相似度**（或归一化后的距离）——不受文本长度影响
- 归一化本质：把不同度量标准统一到同一标尺（如不同科目满分不同，分数要归一才能比）

### 3.2 文档解析（视频10）——面试重灾区

> RAG 面试**最先问文档处理**（判断有无实战经验），不是先问检索/切块

| 文档类型     | 处理工具                      | 说明                                               |
| ------------ | ----------------------------- | -------------------------------------------------- |
| 数字 PDF     | **MinerU**（Python 库）       | 直接转 Markdown 文本，保留表格、版面识别           |
| 扫描版 PDF   | **PaddleOCR**（百度开源免费） | OCR 识别，支持版面/公式识别，轻量高效              |
| 复杂扫描场景 | 千问 3 VL 等多模态大模型      | 精度高但参数量大（8B），资源消耗高，仅复杂场景用   |
| 公式         | 识别后统一转 **LaTeX** 格式   | 用代码形式表示平方、分数、根号、积分等（面试考点） |
| Word 文档    | **Docling**                   | RAG 场景解析质量第一（优于 python-docx）           |
| Excel        | pandas 即可                   | pandas 本身是表格处理工具                          |

- 数字 PDF：由 Word/TXT 转制，可直接提取文字
- 扫描版 PDF：本质是图片，无法直接提取文字，需 OCR
- 配套资料：Z02 文档加工中心

### 3.3 文本切块 · 父子分块（视频11）——★面试必考

**切块原则**
- 不能只按长度切（会把同一句话切两半）
- 优先**按段落/标题层级**切，超长内容再按长度二次拆分
- 切块要设置**上下文重叠**，避免上下文断开

**父子分块（Parent-Child Chunking）——核心答案**
- 一句话总结：**小块检索找得准，大块返回补得全**
  - 先切**父块**（大块：一个章节/整节内容）
  - 再把父块切成**子块**（小块：一段或几句话）
  - 用户提问 → **用子块检索**（小、精准）
  - 命中子块后 → **返回整个父块**给大模型（信息完整）
- 经典例子：游泳池深水区规则
  - 父块 = 深水区完整规则；子块1 = 身高1.4米以上
  - 问"身高1.5米能进吗" → 子块命中"身高1.4米以上"
  - 若只返回子块会答"能进"——**错误**！漏了"必须通过深水测试、必须戴泳帽、禁止跳水"
  - 正确：返回整个父块，回答"身高达标，但还必须通过深水测试、戴泳帽"
- 尤其重要：**医疗、金融场景**（漏一条关联条款=误诊/出错）
- 规则：**子块负责检索，父块负责生成**

**父子分块存储（面试高频）——两种方案**
1. **经典分离式**：子块存**向量数据库**（Milvus / Qdrant，也可提 FAISS 但较老）；父块存**常规数据库**（Redis、PostgreSQL——增强版 MySQL）
   - 优点：向量不变时可编辑版本、可增删改查、方便迭代管理
2. **共存式**：父块、子块都存向量数据库，父块信息以**自定义元数据（metadata）** 形式存储
   - 优点：都在一个库、调用快、运维简单
   - 缺点：元数据没法按数据库方式管理，需人工操作
- **metadata 结合业务**（舆情案例）：存渠道来源（抖音/小红书/315 等），将来可 `if 渠道==315` 直接走规则，省掉大模型调用

### 3.4 稀疏向量与稠密向量（视频12）——★核心考点

**Embedding（嵌入模型）**
- 作用：把文字转化为代表语义的向量
- 相似度：欧氏距离 / 余弦相似度
- 模型优劣判断：语义相近的文本向量位置近、语义差异大的向量区分度高
- 重要性：向量提取出错 → 后续检索全失效（RAG 的基础）

**离线流程完整版**：原始文档 → 文本清洗解析 → 文本切块（父子分块）→ Embedding 向量化 → 存入向量数据库

**向量数据库选型**：Milvus（体量大）、Qdrant（数据量几千万级更轻量）；FAISS 偏老

**在线检索流程**：用户 query → Embedding 转向量 → 混合检索（全文检索 + 向量检索）

**稀疏向量（Sparse）**
- 定义：基于**词表/token 词典**生成，绝大多数维度为 0，仅少量关键词位置有值
- 示例：千问 2.5 7B 词表约 **15 万 token**，对应向量只有少量非零值
- 作用：**关键词检索**（全文检索/BM25），命中关键词数量越多得分越高
- 适用：技术名词、专属代号、无语义字符串

**稠密向量（Dense）**
- 定义：由连续小数组成的一维数组（如 1024 维），**所有维度都是非零小数**
- 作用：**语义检索**，通过向量距离算语义相似度
- 适用：表述不同但语义一致的内容（方言、同义改写）

### 3.5 混合检索与权重融合（视频13）

**多路召回去重**：对稀疏、稠密两路召回结果去重，避免重复文档传入，同时保留两路各自得分

**权重融合法（Weighted）**
1. **归一化**：把稀疏、稠密两路分值统一转换到 [0,1] 区间（Min-Max 或 arctan 等），消除量级差异（BM25 分数无上限、余弦在 [0,1]）
2. **设定权重**：先按业务经验初设（术语多→调高稀疏权重；语义需求高→调高稠密权重）
3. **权重调优**：不能只靠经验，要**构建测评集**，按实际测试效果确定最优配比
4. **总分** = 稀疏归一化分 × 稀疏权重 + 稠密归一化分 × 稠密权重

**RAG 测评指标**
- **Recall@K**：前 K 个结果中相关文档占知识库全部相关文档的比例（召回全面性）
- **Precision@K**：前 K 个结果中真正相关文档的比例（精准度）

### 3.6 排名融合与精排（视频14）

**权重融合 vs RRF 排名融合**
- 权重融合：参考**原始相似度分数**（需归一化）
- **RRF 融合**（Reciprocal Rank Fusion）：完全不看原始分数，只按排名计分
  - 公式：`score = 1 / (K + rank)`，K 为常数（默认 60）
  - 排名越靠前分数越高；适合无明确业务偏好、求稳求便的场景，多数大模型框架默认采用
  - 融合后直接取**融合结果的前 10**，而不是两路各取前 5 再合并

**粗选 + 精排（初选精排）——业界标准（课本内容不符合业界标准）**
- **粗选**：TopK 要设得**大**，保证召回无遗漏，把潜在相关文档全部纳入候选池
- **精排**：用 reranker 模型给候选文本**重新打分排序**，把高相关文档置顶
- 常用精排模型：**BGE reranker**（主流）、**千问 3 reranker**（可选）
- 效果验证案例：退款 FAQ 场景，未开启精排时错误文档排在首位；开启精排后正确文档（覆盖年付条款）置顶

### 3.7 全文检索 · TopK/TopP · 倒排索引（视频05/06/07）

**TopK / TopP（大模型采样概念，面试常考）**
- TopK：只从概率最高的前 K 个词里采样
- TopP：按概率从高到低累加，达到阈值（如 0.9）确定候选池
- 温度（temperature）：控制随机性

**中文分词**
- 中文无天然空格，需分词；主流工具：**结巴分词（jieba）**
- 三种模式（精确/全/搜索引擎）

**倒排索引（Inverted Index）——稀疏检索的底层**
- 正排索引：从"书→段落→句子→词"找内容（图书馆先找书）
- **倒排索引**：从"**词→句子→段落→书**"反着找（先找词）
- 两个步骤：①**建库**（分词过滤→构建索引库，记录词在哪些文档出现+出现次数）②**检索**（用户问题分词→查表→合并去重→评分）
  - 建库一次，可检索无数次
- 分词过滤：一般留名词（动词如"覆盖/提供"通常不要），但按业务调整（退款/投诉类动作词要留）
- **BM25 打分**（全文检索/关键词检索技术）：
  - 核心三句话：词出现次数越多越相关（但加着加着就不加了，防刷分）；越少见的词越值钱（稀有词权重高，必须召回）；长文档不占便宜
  - 例：词出现3次=0.6分，出现2次=1分 → 更稀有的得分更高
- 混合检索 = 关键词检索（BM25）+ 稠密检索；**用了混合检索就别再说"混合+关键词"（重复）**
- **TopK 与阈值（score）**：TopK 决定返回数量上限；阈值过滤低相关干扰项（如相关度<0.7 直接不返回）

### 3.8 向量化总结与就业分享（视频09）

- 文档处理是面试重灾区：数字 PDF vs 扫描版 PDF 区别必答
- 就业参考：往届学员北京 26K offer、最高上海 34K；一线 AI 岗位平均约 18K
- 学习建议：有经验老师带教效率远高于自学

## 四、今日总结（视频15）——RAG 全流程闭环

**RAG 两大核心阶段**：离线建库 + 在线检索；混合检索属于在线检索环节

**检索结果处理规则**：检索返回**子块**，最终给大模型传**更完整的父块**作为上下文，避免信息遗漏

**完整闭环**：用户问题 + 检索上下文 → 大模型 → 输出最终结果

**混合检索两条路**：
- 稀疏向量（关键词检索，倒排索引/BM25）
- 稠密向量（语义检索，Embedding 余弦相似度）

**融合方案**：
- 简化版（业务简单）：省略融合，两路各取部分结果去重 → 直接重排（快但准确率稍低）
- 标准版：融合（权重融合 / RRF 排名融合）→ reranker 重排 → TopK

**重排**：融合后候选需经 reranker（BGE reranker / 千问 3 reranker）逐一打分，高相关排前，TopK 筛选最终结果

| Recall@K / Precision@K        | 召回全面性 / 结果精准度                                      |
